# Phase 5 — Argo CD GitOps — design

## Context

Phase 4 deploys the full stack (Postgres, Liquibase migration, Keycloak, MCP server, UI) onto a local `kind` cluster via `k8s/bootstrap.sh` running `kubectl apply` imperatively, plus two `ConfigMap`s generated at apply-time from source files (`keycloak/realm-export.json`, `db/changelog/`). Phase 5 replaces that imperative apply step with Argo CD: install Argo CD into the same cluster, point one Argo CD `Application` at this repo's `k8s/` directory, and let Argo CD reconcile — a `git push` becomes the deploy mechanism, with drift detection and self-healing for free.

## Key decision: one Application, not an "app-of-apps"

The original phase roadmap sketch called this "Argo CD app-of-apps GitOps." Having now built Phase 4's actual manifests, a genuine app-of-apps split (one child `Application` per component: postgres, keycloak, liquibase, mcp-server, ui) turns out to conflict with the other real improvement this phase should make: replacing the two imperatively-generated `ConfigMap`s with a proper declarative Kustomize `configMapGenerator`, so Argo CD manages 100% of the stack from git with no pre-sync shell step. Argo CD's `directory.include`/`exclude` glob-based sub-selection (which would let several `Application`s share one flat directory) only applies to its plain "directory" source type, not to a Kustomize source — and a single `kustomization.yaml` is what makes the `ConfigMap` generation declarative. Splitting into 5 separate Kustomize overlays to preserve a 5-app split would add real structural complexity (multiple kustomization bases/overlays) for a 5-service, single-team local demo with no independent deployment cadence between its components — the same YAGNI judgment this project has already applied elsewhere (e.g. Phase 3's spec: "No connection pooling... acceptable latency for a demo whose point is the auth/scoping story"). **One Argo CD `Application`, Kustomize-sourced, automated sync + self-heal + prune, is the design** — still genuinely GitOps (this is a common, legitimate pattern for single-team clusters), just without inventing multi-app indirection nothing in this project needs.

## What changes

1. **`k8s/kustomization.yaml`** (new) — lists all 8 existing manifest files as `resources:`, and adds two `configMapGenerator` entries replacing `bootstrap.sh`'s imperative `kubectl create configmap --from-file=...` calls:
   - `keycloak-realm-export` generated from `../keycloak/realm-export.json` (key `realm.json`, matching what `k8s/04-keycloak.yaml` already mounts).
   - `liquibase-changelog` generated from `../db/liquibase.properties` plus every file in `../db/changelog/` (matching what `k8s/05-liquibase-job.yaml`'s `items:` list already expects — same keys, same values, just generated by Kustomize instead of a shell command).
   - Kustomize's default behavior appends a content hash to generated `ConfigMap` names (`keycloak-realm-export-a1b2c3d4`) and auto-updates every reference to the new name on each change — this is Kustomize's own drift/rollout mechanism (a changed realm export or changelog automatically triggers new Pods that mount the new `ConfigMap`, instead of Phase 4's static-named `ConfigMap`s which a running Pod wouldn't automatically pick up). `k8s/04-keycloak.yaml`/`k8s/05-liquibase-job.yaml`'s `configMap.name: keycloak-realm-export`/`liquibase-changelog` references keep their base names unchanged in source — Kustomize's `nameReference` transformer rewrites them at build time.
   - `disableNameSuffixHash: false` (the default) is kept deliberately — this is a genuine improvement over Phase 4's static-named ConfigMaps, not a regression, and is called out explicitly in Verification below.
2. **`argocd/`** (new directory):
   - `argocd/install.sh` — applies Argo CD's official install manifest (`https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml`) into a new `argocd` namespace, waits for the `argocd-server` Deployment to become ready.
   - `argocd/application.yaml` — the single `Application` resource: `spec.source.repoURL` = this repo's GitHub URL, `spec.source.targetRevision` = a parameter (documented, defaults to the current working branch for local-demo convenience; a real deployment would point at `main`), `spec.source.path: k8s`, `spec.destination` = the same cluster's `financial-mcp` namespace, `spec.syncPolicy.automated: { prune: true, selfHeal: true }`.
3. **`argocd/bootstrap.sh`** (new) — the Phase 5 one-command entry point: creates/reuses the `kind` cluster (reusing `k8s/kind-config.yaml`), builds and loads the three local images exactly as `k8s/bootstrap.sh` already does (images still can't come from git — no registry in this local setup, so this remains an imperative step even under GitOps), installs Argo CD (`argocd/install.sh`), applies `argocd/application.yaml`, waits for the Application to reach `Synced`/`Healthy` via `argocd app wait` (or polls `kubectl get application` status if the `argocd` CLI isn't installed — check for it and degrade gracefully with a clear message), then prints next steps (verification commands, Argo CD UI access).
4. **Requirement:** since Argo CD pulls from `repoURL`, the working branch must be pushed to `origin` before `argocd/bootstrap.sh` can sync anything — this is the one genuinely new operational step GitOps introduces (Phase 4's `kubectl apply` never needed the branch pushed anywhere). `argocd/bootstrap.sh` checks this (`git status` ahead/behind, or simply a clear README-documented prerequisite) rather than silently producing a confusing "app stuck in OutOfSync/Unknown" state.

## Non-goals

- No app-of-apps / multi-`Application` split (see decision above).
- No Argo CD SSO/RBAC hardening, no Ingress for the Argo CD UI itself (`kubectl port-forward` to reach it, consistent with this project's whole local-demo posture).
- No Helm — Kustomize only, matching what's already in `k8s/`.
- No CI/CD pipeline triggering the git push itself — this phase proves the GitOps *mechanism* (git state → cluster state, automatically), not a full CI story.
- No image-registry / automated image-tag-bump-on-push story — images stay locally built-and-loaded via `kind load docker-image`, as in Phase 4; true GitOps image promotion (Argo CD Image Updater or similar) is out of scope for a local demo with no registry.

## Verification

```bash
git push -u origin claude/db-schema-rls   # Argo CD needs a real remote to sync from
argocd/bootstrap.sh
kubectl get application -n argocd financial-mcp -o wide   # Synced, Healthy
pip install -r scripts/requirements.txt -r ui/requirements.txt
python3 scripts/verify_scopes.py
python3 scripts/verify_mcp_server.py
python3 scripts/verify_ui.py
java -jar karate/karate.jar karate/scoped_access.feature
```
All four verification layers must pass with the same counts as Phase 4's direct-`kubectl-apply` deployment — proving Argo CD's Kustomize-built output is identical to what `k8s/bootstrap.sh` applied directly.

**GitOps proof (the actual point of this phase):** make a small, reversible change to a tracked file (e.g. edit a comment or a non-functional label in `k8s/07-ui.yaml`), commit, push, and watch `kubectl get application -n argocd financial-mcp -w` (or the Argo CD UI) pick up the change and reconcile automatically within its poll interval — without running `kubectl apply` by hand. Revert and push again to restore the verified-good state.

## Open questions / explicitly deferred

- `argocd/bootstrap.sh` degrades to polling `kubectl get application` status if the `argocd` CLI binary isn't installed locally, rather than requiring a new dependency just for this phase's convenience.
- Teardown: `kind delete cluster --name financial-mcp` remains the reset button, same as every prior phase — Argo CD's own state lives inside that same cluster, nothing external to clean up.
